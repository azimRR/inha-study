So who gives the CPU back? Two answers in history:
A process runs on the real CPU, with the real registers.
That is why it is fast — and why it is dangerous: while it
runs, the kernel is not running.
Two names
Interrupt — a hardware
signal that makes the CPU
stop what it is doing and
run a kernel routine
(the handler) — the same
idea as a signal handler,
one floor down.
Preemption — taking the
CPU from a process that
did not ask to give it up.
The process never notices;
it wakes up later with its
registers (context switch)
exactly as they were.

What the Scheduler Decides, and for Whom
9/15/2026
SOC 3010              j.yusupov@inha.uz
CPU Scheduling
Throughput
A compiler, a video encode, a database rebuild. Wants
throughput: jobs finished per hour. Does not care whether it
waited 3 s to start.
Latency
Your editor, a shell, a game. Wants latency: the time between a
key press and the screen reacting, ideally under ~50 ms. Does
not care how long it takes to finish, because it never finishes.
Why this is a fight
Every millisecond the
CPU spends switching
to the editor is a
millisecond the encode
did not get. There is no
setting that makes both
happy; there is only a
choice of whom to
disappoint, and by how
much.
Two customers who want opposite things

## Page 13

Round Robin (RR)
9/15/2026
SOC 3010              j.yusupov@inha.uz
CPU Scheduling
• Each process gets a small unit of CPU time (time quantum q), usually
10-100 milliseconds.  After this time has elapsed, the process is
preempted and added to the end of the ready queue.
• If there are n processes in the ready queue and the time quantum is q,
then each process gets 1/n of the CPU time in chunks of at most q time
units at once.  No process waits more than (n-1)q time units.
• Timer interrupts every quantum to schedule next process
• Performance
• q large FIFO
• q small q must be large with
respect to context switch,
otherwise overhead is too high
(time quantum 4)

## Page 17

MLFQ: Learning the Future from the Past
9/15/2026
SOC 3010              j.yusupov@inha.uz
CPU Scheduling
SJF is optimal and impossible: nobody knows a job's length in advance.
The multi-level feedback queue (MLFQ) guesses it from the job's past.
•
Key Rule: Always run the highest queue first. Only go to a
lower queue when the higher one is empty.
•
If a process finishes within its time quantum →
 Great! It's
done.
•
If a process doesn't finish →
 It gets demoted (pushed
down) to the next queue.
•
This is the "feedback" — the system learns: "This process
needs more time, let's give it a bigger slice but lower priority."
