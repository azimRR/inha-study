Message passing— and Why Not Just Use a File
9/21/2026

Why not a shared file?
You can, and it is wrong on four counts:
1. No notification. Nothing wakes you when data lands; you must keep re-reading and asking.
2. No boundaries. A file is bytes; where one message ends is your problem.
3. Racing offsets. Two writers with two independent file positions overwrite each other — and two
writers who share one position do something stranger still.
An operating system's first job is to keep processes apart, and that immediately creates
its second job: giving them a safe way to cooperate anyway.

What is a PIPE?
A pipe is a fundamental mechanism for Inter-Process Communication (IPC)
in Unix-like operating systems.
Imagine it's a one-way water pipe connecting two points.
•
One process writes data to one end. ✍
•
Another process reads that data from the other end. 📖
•
It's a unidirectional (one-way) communication channel.
•
The data flows in a First-In, First-Out (FIFO) manner.
A pipe can be created using the system call pipe
#include <unistd.h>

Pipes
pipe(int fd[2]): One Call, Two Ends
The mnemonic that saves you an hour
0 is stdin-like, so it is where you read.
1 is stdout-like, so it is where you write.
A pipe is a nameless, fixed-size buffer inside
the kernel with two descriptors on it:
fd[0] the read end, fd[1] the write end.
pipe capacity — the buffer's size: 65536 bytes (64 KiB) on Linux since kernel 2.6.11;
before that it was one page.
A pipe is like a file because the kernel represents each end with a file descriptor, so
processes can use read(), write(), and close() on it just as they would on an open file.

Four open ends means the kernel sees

In particular it will not declare the

The standard [Correct] flow of operation is:
•
A process creates a pipe; then it performs a fork
•
The child processes inherit the file descriptors
•
One of the two processes (e.g. father) writes in
the pipe while the other (e.g. child) reads from the pipe
•
The unused descriptor can/MUST be closed
[fork clones the parent's file descriptor table not the pipe]

dup2
Redirecting Process I/O
dup2 copies over file descriptor information from one file descriptor number
(srcfd) to another (dstfd).
int dup2(int srcfd, int dstfd);
e.g. dup2(3, 1);
// duplicates from 3 -> 1; FD 1 now also refers to what 3 is referring to.
•
Both will now refer to the same thing (e.g. if you read from one, it will advance
the position of the other).
•
If dstfd is already open, it is closed before being used.

Full program with dup2
exec Keeps the Descriptors — That Is the Whole Trick
execve throws away the program image — code, heap, stack, everything — and keeps the
descriptor table
// In the child for the `ls`:
dup2(p[1], 1);
// 1. Rewire stdout to the pipe
close(p[0]);
close(p[1]);
// 2. Close unused ends
execlp("ls", "ls", NULL);
// 3. Replace memory with `ls`
We use dup2 to secretly rewire the child's stdout to the pipe and close the leftover ends to
ensure proper EOF, then exec replaces the child with ls. Because exec preserves the file
descriptor table, ls blindly writes to stdout and unknowingly (we abstract the pipe away) sends its
output straight into the pipe instead of the terminal.
